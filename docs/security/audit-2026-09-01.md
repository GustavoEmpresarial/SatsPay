### O que foi feito

- **C2** — `client/nginx.conf` passou a **sobrescrever** `X-Forwarded-For` com
  `$remote_addr` (antes anexava via `$proxy_add_x_forwarded_for`), e
  `client_ip.rs` passou a preferir `X-Real-IP` e a ler o **último** elemento do
  XFF em vez do primeiro. Verificado em produção: requisição com
  `X-Forwarded-For: 66.66.66.66, 77.77.77.77` é resolvida como o peer real.
- **C3** — novo `api-http/src/rate_limit.rs`: janela fixa por IP e por classe de
  rota, sem dependência nova. `login`/`register` 10/5min, faucet 20/5min,
  saques 20/5min, demais rotas `/v1/auth/*` 300/5min, resto 600/5min.
  Responde `429` com `Retry-After`. Verificado em produção.
  *Limitação consciente: contadores em processo, portanto o teto é por réplica.*
- **M7** — o extractor `AuthUser` passou a reler a conta no banco em vez de
  confiar nos claims: conta apagada é rejeitada na hora e o `role` vem sempre
  fresco (admin rebaixado perde privilégio imediatamente, não em 15 min).
- **M8** — `TimeoutLayer` de 30s como camada mais externa.
- **A5** — `ADMIN_EMAILS=contato.pessoal.010@gmail.com` no `.env` da VM.

### ⚠️ Ressalva sobre A5: admin ainda não consegue entrar

`AuthService::login` com `admin_gate` **sempre** exige OTP por e-mail, e o SMTP
está desativado (`SMTP_ENABLED=false` → `NoopEmailSender`, que loga apenas
destinatário e assunto, **nunca o código**). Consequência: a tela
`/admin/login` fica inacessível até existir um SMTP real. As rotas de admin da
API funcionam via login normal (o usuário é promovido a `ADMIN` no próximo
login), mas o painel dedicado não. **Configurar SMTP é pré-requisito real do
fluxo de admin, não um extra.**

### ⛔ Nota sobre A4: `NODE_ENV=production` derrubaria a API hoje

Trocar para produção **não é** uma mudança de configuração isolada. Com a
config atual (`ALLOW_STUB_CHAIN=true`, `USE_REAL_CHAIN_CLIENTS=false`),
`chain::registry::build_stub_client` chama `assert_stub_client_allowed`, que
retorna `ForbiddenInProduction` — e `api-server::main` faz
`.expect("failed to build chain registry")`, ou seja, **panic no boot**.
Em paralelo, `TURNSTILE_SECRET="disabled_in_dev"` vira
`CaptchaError::NotConfiguredInProduction`, quebrando faucet e registro.

Não existe "produção com captcha desligado": o fail-closed é intencional
(ADR 0008). Ir para produção exige, juntos: chain clients reais configurados
(`deposit_xpub`, WIF da hot wallet, endpoints, `CHAIN_NETWORK`) **e** um
`TURNSTILE_SECRET` válido. Mantido em `development` até lá.

Mitigação no intervalo: com C2 e C3 corrigidos, o farming de faucet deixou de
ser trivial mesmo com o captcha inativo (cooldown por IP voltou a valer, e há
limite de 20 req/5min por IP na rota).

## C1 — Aplicação em HTTP puro (sem TLS)

`bitcosats-client` publica `0.0.0.0:4500->80`. Não há TLS em lugar nenhum do
caminho do BitcoSats. Verificado: `https://169.58.45.155:4500` não responde.

**Impacto.** Tudo trafega em claro e é capturável por qualquer intermediário
(provedor, rede do usuário, backbone): senha no `POST /v1/auth/login`, códigos
OTP, **access token e refresh token** em toda requisição autenticada, endereços
de depósito/saque. Um atacante on-path rouba a sessão e, com o OTP capturado,
autoriza saques.

Existe um **Caddy** na mesma VM já emitindo Let's Encrypt para outros domínios
(`/root/shared-proxy/Caddyfile`), mas o BitcoSats não está roteado por ele.

**Correção.** Apontar um domínio para a VM e adicionar um bloco no `Caddyfile`:

```
bitcosats.exemplo.com {
	reverse_proxy 127.0.0.1:4500
}
```

Depois: parar de publicar `:4500` em `0.0.0.0` (bind em `127.0.0.1`), e marcar
os cookies/refresh como `Secure`.

## C2 — `X-Forwarded-For` confiado sem validação

`crates/api-http/src/client_ip.rs::resolve_client_ip` pega o **primeiro** valor
de `X-Forwarded-For` direto do header, sem lista de proxies confiáveis:

```rust
if let Some(xff) = parts.headers.get("x-forwarded-for")... {
    if let Some(first) = xff.split(',').map(str::trim).find(|s| !s.is_empty()) {
        return Some(first.to_string());   // <- controlado pelo cliente
    }
}
```

O nginx usa `proxy_add_x_forwarded_for`, que **anexa** o peer real ao valor
enviado pelo cliente. Como o código lê o **primeiro** elemento, o valor que vence
é o do atacante. Explorável hoje, em produção.

**Impacto.**
1. **Bypass total do `allowed_ips` das API keys** (`db::public_api::check_usable`).
   Uma chave roubada e restrita a IPs específicos é usável de qualquer lugar.
2. **Bypass do anti-Sybil do faucet.** `db::faucet::claim` faz cooldown por IP
   (com `pg_advisory_xact_lock`) — boa lógica, mas o IP é forjável. Rotacionando
   o header, o atacante drena o inventário HOUSE. Combinado com o **A4**
   (captcha desativado), o faucet está efetivamente aberto.
3. **Poluição de auditoria** — `withdrawals.requested_ip` é escolhido pelo atacante.

**Correção (uma linha, imediata).** Em `client/nginx.conf`, sobrescrever em vez
de anexar:

```nginx
proxy_set_header X-Forwarded-For $remote_addr;
```

**Correção no código (definitiva).** Preferir `X-Real-IP` (que o nginx já define
como `$remote_addr`) sobre o `X-Forwarded-For`, ou parsear o XFF **da direita
para a esquerda**, descartando N hops confiáveis configurados por env.

## C3 — Ausência de rate limiting

Não existe nenhum rate limit HTTP no workspace. `api-http/src/lib.rs` monta o
router só com `PrometheusMetricLayer`. O único controle de frequência é o de OTP
(`otp_resend_cooldown_secs`, `otp_max_attempts`) dentro do `AuthService`.

**Impacto.** `POST /v1/auth/login` aceita tentativas ilimitadas de senha, por
conta e por IP. Também sem limite: `/v1/auth/register` (spam de contas),
`/v1/deposits/address/:coin`, e as rotas da API pública.

> Nota de procedência: o `middleware.rs` foi reconstruído por mim nesta sessão
> (o original havia sido perdido). O legado Node tinha `middlewares/rateLimit.ts`.
> É possível que o original em Rust tivesse rate limiting e minha reconstrução o
> tenha omitido — **conferir contra o repositório original quando recuperado.**

**Correção.** `tower-governor` (ou um limiter próprio em Postgres/Redis) por IP
real + por conta, mais agressivo em `/v1/auth/*`. Somar backoff exponencial e
lockout temporário por conta após N falhas.

## A4 — Instância rodando em modo desenvolvimento

No compose da VM: `NODE_ENV: development`, `TURNSTILE_SECRET: "disabled_in_dev"`,
`ALLOW_STUB_CHAIN: "true"`, `USE_REAL_CHAIN_CLIENTS: "false"`.

`captcha::TurnstileVerifier` trata `"disabled_in_dev"` como **bypass incondicional**
fora de produção (é erro fatal se `NODE_ENV=production` — o fail-closed está certo,
só não está ativo). Resultado: **o captcha do faucet e do registro não valida nada.**

**Correção.** `NODE_ENV=production` + `TURNSTILE_SECRET` real. Isso também força a
decisão consciente sobre os chain clients (o stub é proibido em produção por
`chain::policy::assert_stub_client_allowed`).

## A5 — `ADMIN_EMAILS` vazio

`/root/bitcosats/.env` tem `ADMIN_EMAILS=`. Em `AuthService::login` o papel é
sincronizado do allowlist a cada login:

```rust
} else if !should_be_admin && user.role == "ADMIN" {
    self.repo.update_user_role(user.id, "USER").await?;
```

Com a lista vazia, **todo ADMIN é rebaixado para USER no próximo login** e o
painel administrativo fica inacessível — incluindo aprovação de saques acima do
threshold, que ficam presos em `PENDING` para sempre.

**Correção.** Preencher `ADMIN_EMAILS` com os e-mails operacionais reais.

## M6 — Vazamento de erro interno nas respostas

Padrão presente em praticamente todas as rotas:

```rust
Err(e) => (StatusCode::INTERNAL_SERVER_ERROR, Json(json!({ "error": e.to_string() })))
```

`sqlx::Error` renderiza detalhes de query/constraint/coluna. Entrega ao atacante
um mapa do schema.

**Correção.** Mapear erro → código estável (`{"code":"INTERNAL"}`), logar o
detalhe server-side com um `request_id` e devolver só o id ao cliente.

## M7 — Sessão: revogação e papel

- Access token HS256 com TTL 900s e **sem lista de revogação**. Logout revoga
  apenas o refresh token; o access token continua válido até expirar. O mesmo
  vale para troca de senha e desativação de conta.
- `require_admin` (em `middleware.rs`) lê `user.role` **do claim do JWT**, não do
  banco. Um usuário rebaixado mantém privilégio de admin por até 15 minutos.
- O extractor não revalida se o usuário ainda existe / não foi bloqueado.

**Correção.** Para rotas de admin e de movimentação de valor, reconsultar o papel
no banco (o fluxo de saque já faz isso certo para o 2FA — reconsulta
`get_user_by_id` em vez de confiar no claim `two_factor`). Opcional: `jti` +
tabela de revogação, ou reduzir o TTL.

## M8 — Sem timeout de requisição

`tower-http` está nas dependências com a feature `timeout`, mas nenhum
`TimeoutLayer` é aplicado. Também não há `TraceLayer` nem `CorsLayer`.
(A ausência de CORS não é vulnerabilidade — é restritiva; e o axum já impõe
limite de corpo de 2 MB por padrão.)

**Correção.** `.layer(TimeoutLayer::new(Duration::from_secs(30)))`.

---

## M9 — AES-GCM sem AAD

`crypto::SecretsService::encrypt/decrypt` usa `Payload { msg, aad: &[] }`. Sem
dado associado, um ciphertext é válido em qualquer contexto: com acesso de
escrita ao banco, dá para mover o `totp_secret_enc` de um usuário para outro, ou
o `key_enc` de uma API key para outra, e o serviço decifra normalmente.

**Correção.** Vincular o AAD ao contexto, ex. `aad = b"api_key:" || key_id` e
`aad = b"totp:" || user_id`.

Menor, na mesma área: nonce de 96 bits aleatório (limite de aniversário em ~2^32
mensagens — folgado para o volume atual) e HKDF com salt vazio.

## B10 — `/metrics` sem autenticação

`api-http/src/lib.rs` expõe `/metrics` sem gate. Hoje **não é alcançável de fora**:
`api-server:4000` não é publicado no host e o nginx só faz proxy de `/v1/` e
`/healthz`. Fica como defesa em profundidade — se alguém adicionar uma regra de
proxy, vaza inventário de rotas e volumetria.

*(Verificado durante a auditoria: a porta `0.0.0.0:4000` da VM é um `socat` para
`127.0.0.1:4100` de **outra** aplicação, não do BitcoSats.)*

## B11 / B12 — Menores

- **Argon2** usa `Argon2::default()` — m=19 MiB, t=2, p=1. É o mínimo OWASP;
  considerar m=64 MiB.
- **`allowed_ips`** compara string exata (`ip == source_ip`), sem CIDR nem IPv6
  normalizado. Documentar ou implementar CIDR.
- **Enumeração**: `register` distingue e-mail/username já existente (`Conflict`), e
  `verify_signed_request` distingue `KeyNotFound` de `SignatureMismatch`.
- **API keys recuperáveis**: `key_enc` guarda a chave crua cifrada (necessário
  para verificar assinatura HMAC). Dump do banco + `ENCRYPTION_KEY` = todas as
  chaves. Inerente ao desenho; reforça a importância da custódia da
  `ENCRYPTION_KEY` (hoje em `.env` no disco da VM, `0600 root`).
